AP Intake Agent

An accounts-payable invoice-intake agent. A demo built by Noel Turlington.

What it does

An email arrives with an invoice, in the body or as an attachment. The agent extracts structured invoice data, checks it against PO records, the vendor master and the payment ledger, and asks an LLM only when a case is genuinely ambiguous. It then posts to a mock ERP or queues the invoice for a person to approve, and logs every step to an append-only audit trail.

52/56golden cases pass (92.9%), mock mode

Architecture

One case moves through pipeline.py in this order. Each stage is a module in src/apintake/.

  1. ingest.pydeterministic

    Loads the raw message and attachments from data/inbox/.

  2. extract.pyLLM, cheap

    Pulls invoice fields into a strict Pydantic schema. One retry with the error fed back. Not an invoice: rejected. Failed twice: queued for review.

  3. validate.pydeterministic

    Math, PO, vendor, duplicate and price-history checks. Zero issues: post. Blocking error: queue. Ambiguous warning only: judge.

  4. judge.pyLLM, stronger

    Runs only on ambiguous warnings. Approve with confidence >= 0.85: post. Anything else: queue.

  5. approve.pyhuman

    Review queue (apintake review). A person approves, which posts, or rejects.

  6. post.pydeterministic

    Appends the invoice to the mock ERP ledger.

  7. audit.pydeterministic

    Every stage writes an event here with its actor: deterministic, llm or human. apintake trail <case_id> prints one case's trail.

Deterministic, LLM or human

The pipeline has 2 LLM call sites. In the golden dataset, 38 of 56 cases resolve with no LLM decision affecting the outcome.

The four failures are intentional. Cases 053 to 056 each sit on a documented threshold, and their golden labels encode a plausible naive expectation:

  • case-053: "Cascade Supplies" scores 0.703 against "Cascade Office Supply", just under the 0.72 fuzzy cutoff. It queues as an unknown vendor. A tuning candidate.
  • case-054: price moved exactly 10.0% (22.00 to 24.20). The drift check is strictly greater than 10%, so it auto-posts. A product question.
  • case-055: the label assumed confidence must exceed 0.85. The code uses >= 0.85. The label is wrong, the system is right.
  • case-056: invoice number INV-0500 matches a posted invoice from a different vendor. Duplicate detection is vendor-scoped, so it auto-posts. A known scope limit.

Failure handling

Only non-invoices are rejected automatically. Every other failure goes to the review queue with its reasons, and every step lands in the audit trail.

  • Math mismatch: blocking error in validate.py. Queued for review with the exact reason. Never auto-approved.
  • Duplicate invoice: same vendor and invoice number as a ledger entry. Blocking error, queued. No LLM involved.
  • Missing PO: one of the ambiguous issues sent to judge.py. A confident approval posts. Anything else queues with the model's rationale.
  • Low confidence: confidence below 0.85, or a reject or escalate decision, goes to the queue. The reviewer sees why the system was unsure.
  • Extraction fails twice: queued for review. No crash, no silent bad data.
  • No API key and no --mock: prints a message and falls back to mock mode.

The review queue (apintake review) shows the reasons, the extracted invoice and the resolved vendor name. The audit trail is append-only JSONL; apintake trail <case_id> prints it.

How to run

Mock mode needs no API key. It reads fixture data instead of calling the API.

cd ap-intake-agent
uv sync

# Run the eval harness (hermetic, mock mode, no API key needed)
uv run apintake eval --mock

# Run one case end-to-end and inspect its audit trail
uv run apintake run --mock data/inbox/case-001.json
uv run apintake trail case-001

# Run every case in the inbox
uv run apintake run --mock --all

# Work the human review queue interactively (approve/reject)
uv run apintake review

Real mode needs ANTHROPIC_API_KEY: drop --mock from any run or eval command.

Extraction uses the cheap model, claude-haiku-4-5. Judgment uses the stronger claude-sonnet-5, because its opinion decides whether money moves without a human.

Decisions

2026-07-21

Auto-post on zero issues, or a judged approval at high confidence

Otherwise the judgment step would never resolve anything by itself.

2026-07-21

Never auto-reject a real invoice

Only non-invoices are rejected. Auto-rejecting a business failure could discard a legitimate invoice no one ever sees.

2026-07-21

Duplicate detection scoped to vendor and invoice number

Invoice numbers collide across vendors. The cost: a spoofed number under a different vendor name gets through.

2026-07-21

Haiku for extraction, Sonnet for judgment

Effort scales with how much the decision matters.

2026-07-21

Eval runs on isolated scratch copies

Repeatable runs, and duplicate checks do not depend on case order.

2026-07-21

Four boundary failures kept in the golden set

They expose real threshold choices instead of reporting 100%.

Limits

  • The ERP, vendor master and PO records are mock JSON fixtures, not a live system.
  • All 56 cases are synthetic.
  • The same author wrote the pipeline and the golden labels. One label (case-055) was itself wrong.
  • Mock mode reads fixtures, so the eval never exercises the LLM calls. The real-mode path was not run during this build because no API key was present; the only earlier live run on record is the 2026-07-21 session whose ledger write was reset before the first commit.
  • Duplicate detection misses invoice-number reuse across vendors.
  • The ROI split comes from this synthetic dataset. A real client's mix will differ.
